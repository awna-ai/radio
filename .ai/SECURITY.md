# Security: radio

**Last reviewed:** 2026-11-21, with network records, keys and stores (§ *Several networks*). This
model describes the design every step is held to, and each step that builds a boundary updates its row.

## What this system is

A daemon, one per computer, that local apps share for rooms, the deliberation protocol and the link to
other computers (partly built). It stores what its clients post and what other computers send; it
reads none of the user's own files, except a file an app hands it to send to another computer, and
runs no model. The worst outcome is a stranger getting a say in it: an
app may hand remote operations to its own handler through Radio, so a hole in Radio's
admission is a hole in that app's remote control, even though Radio never reads those messages.
The second worst is a file meant for one of the user's computers reaching anyone else, or landing
anywhere on the receiving computer but the folder its app chose.
Once a computer is in several networks (designed: § *Several networks*), two more rank beside
these: a private network's content reaching a public one without the person's review, and text from
a less trusted network acting on a more trusted one.

## The link (being built: the key, the endpoint builder, the wire, the fleet record, join codes, joining, accepting, leaving, removing and blocking, and each computer's signed record, in the library; the daemon listens on its link addresses and joins, removes and leaves over them)

The first link is direct only: two computers that can already reach each other (on one network, or
over a VPN the user runs) dial each other at addresses the user configured (D15). There is no relay
and no port mapping yet. Address lookup is in memory only: mDNS stays off by decision, since it would announce
the computer's key on whatever network it is on and can't cross the VPN the link is built for, and
the addresses a computer last used already cover reconnecting on one network. Each row below whose proof says **not built** is the
design the step that builds it is held to; that step replaces the proof with its tests. The steps, in
order: the endpoint and the computer's key; the wire protocol; the fleet record and join codes;
joining, accepting, leaving, removing and blocking; direct addresses; app delivery.

- **Identity is the key, and only the key.** A computer is its Ed25519 key (one per membership, once a
  computer is in several networks: D30); its endpoint id is the public half. The transport's TLS 1.3 handshake proves both ends hold their keys: the dialer's check
  pins the key it dialed, and the listener learns the dialer's key. A name, a fleet id, a version or
  an address a peer sends is a claim, checked against Radio's own records or ignored; it never
  identifies anyone.
- **Admission is Radio's, at the handshake, and again on every stream.** The transport lets any key
  complete a handshake with a listening endpoint. Radio's hook, which runs once the handshake
  completes and before the connection is handed to Radio, refuses every key that is not an accepted
  member on ALPNs `radio/1` and `radio-gossip/1`. A key Radio does not know passes only on the join ALPN `radio-join/1`,
  only while an unused, unexpired join code exists, and then only for the join (its own row). A
  refusal closes with one close code and an empty reason, so it tells the peer nothing. Applying a
  removal or a block closes that key's open connections in the same step, membership is checked
  again on each stream Radio accepts, and Radio never dials a removed or blocked key.
- **Nothing is replayable.** The transport's packets are bound to the connection's keys. Radio never
  sends 0-RTT (its dials keep no TLS session tickets) and never takes a connection before its
  handshake completes, so any early bytes a resuming peer sends are read only after admission; the
  transport's resumption sessions are single use. Signed records that can be forwarded over a fresh
  connection (introductions, removals, leaves, computer records) carry a version or a counter from
  their signer, and a repeated one is dropped; nothing makes counters rise, so a record held back
  and sent late is still applied once (a gap below).
- **What the transport does on its own.** The transport always runs QUIC NAT traversal, which 1.3.0
  cannot switch off: once connected, each side tells the other its bound addresses (every interface's only when bound to
  `0.0.0.0` or `[::]`, which Radio never does) and probes up to 32 addresses the other names. Radio
  limits who can reach it by binding only the local addresses the user configured, never every
  interface, and accepts the rest as a gap.
- **Raw files rest only where an app asked.** A delivered file is written only into the folder the
  receiving app registered; Radio keeps no copy of its contents on either side, and a send that can't
  reach its peer fails within the dial's 5 seconds rather than waiting in Radio.

The numbers each step tests: at most 32 link connections from other computers at once and, apart
from them, 64 this computer dialed, each 4 per key, and 4 joins; 16
bidirectional streams open at once per connection and one unidirectional stream for the fleet topic; Radio closes a
connection with no open stream for 11 minutes (the transport's keep-alives don't count); the dialer
closes an unused, unkept connection after 10 minutes. Kept connections heartbeat every 15 seconds
and fail after 45 seconds without a successful heartbeat, then retry with backoff from 1 second
to 60 seconds, starting over only after a connection stayed up for 15 seconds. Kept lists live only in memory, with at most 64 entries per app; a frame is
read whole within 5 seconds of its stream being accepted; a file being delivered fails if no byte
arrives for 30 seconds; at most 4 files arriving at once and 1 per key; a file must arrive
whole within 120 seconds of its stream; a dial gives up after 5 seconds;
one delivery folder holds at most 64 waiting files and 1 GiB; a file is refused unless 256 MiB stays free after it and every
file arriving.
App messages have an 8 KiB decoded body cap, a 120 second clock window either way, and a per-sender
replay set holding at most 1,024 ids for 300 seconds without evicting live ids.
At most 4 handlers run at once and 1 per sender, with a 30 second deadline and a reply of at most
4 KiB and 8 lines, checked on both the target and sender; replies exclude controls except newline
and tab, and exclude the invisible characters that room text replaces with spaces.
A handler's process group, including grandchildren, and the handler's own pid are killed when the
handler ends, at its deadline or on excess stdout; its pid stays reserved until then, so neither
signal can reach a reused id, and the handler is reaped after.
The audit log writes only valid app names and limits `not_member` lines to 1 per sender key and
60 overall in any 60 seconds; other refusal reasons are not rate-limited.
The shared rule and audit-name checks are tested in `crates/radio-link/src/handler.rs`, the shared
handshake and stream audit budget with paused time in `src/admit_tests.rs`, and hostile replies at
the sender in `tests/wire.rs::sender_rejects_hostile_reply_text`.
`crates/radio/src/handler_tests.rs` tests invisible replies, short audit lines and cleanup of
background children on normal exit, including children that keep stdout open.
At most 4 socket messages wait independently of file sends; their outer wait is 45 seconds and
the client waits 60 seconds.

## Several networks (keys and stores built; endpoints and other controls designed)

A computer may belong to several networks at once (D30). Each network has one access scope, which the
person sets on their own computer: `personal` (the person's own computers, today's fleet), `internal`
(a group the person trusts, such as a team, a household or a lab) or `external` (a group the person
does not trust with what they hold). Personal and internal networks are private; external ones are
public. A new network is internal until the person marks it external (the join asks for the scope
before any room syncs), and another member may mark the same network differently on their own
computer. An ordinary computer is in one personal network, its owner's, and at most 8 other networks.
A shared computer (one with no person at it, such as a home server) may also be in several people's
personal networks; it keeps every membership apart, and its personal memberships carry rooms only
(N8).

The worst outcomes here, in order: content from a private network reaching a public one without the
person's review; text from a less trusted network acting on a more trusted one (an agent taking it as
an instruction, a turn it starts, an app operation it runs); one network's peer reaching another
network's rooms, records, computers or apps; and a network learning this computer's other
memberships, its addresses, or who its owner is elsewhere.

The store's `networks` table, the person's scope mark and the caps of one personal and 8 other
networks are built and tested in the store (`crates/radio-link/src/fleet_db_tests.rs`); the personal
row follows the fleet. `network_init` with `internal` or `external` scope now makes a network with
its own key (`networks/<id>.key`) and recovery file (`networks/<id>.recovery.key`) in the link
folder, and store (`networks/<id>.db`) beside `fleet.db`. N2 is built for keys and stores, tested in
`key_tests.rs`, `fleet_db_tests.rs` and `crates/radio/src/server_tests.rs`; endpoints are the next
step. `network_scope_set` re-marks any non-personal network in the index; the personal network's
scope stays fixed. `network_list` lists every network in the index; the network ops other than
`network_list`, `network_init` and `network_scope_set` still serve only the personal network. No
other control N1 to N15 is built. Each row marked **not built**
remains the design that the step building it is held to: that step replaces **not built** with its
tests and names the control it proves. The fleet rows below (§ *Trust boundaries* and the gaps) keep
holding for the personal network.

A founder-signed record may change its admitters, moderators and links; a recovery-signed one
keeps them unchanged. Empty lists keep the personal record's bytes and signature.

### What may cross: the controls

- **N1. One network per room.** Every room belongs to exactly one network, fixed when it is opened. No
  op moves a room or copies a message between networks, except the person's own carry (N6) and a
  link's shared rooms (N7). Radio refuses a room message, seat request or result that arrives on a
  connection whose network isn't the room's, or, for a shared room, isn't a network linked to it.
  Test: a member of one network posting into another network's room on this computer is refused.
- **N2. A key and an endpoint per membership.** `node.key` is only an ordinary computer's personal
  identity, and a shared computer's first personal one. Every other membership has its own key and
  its own endpoint and UDP socket (the transport's endpoint has exactly one id). Separate keys and
  stores are built; endpoints remain unbuilt. Test: the peers of
  two networks see two different keys, and nothing either network is served names the other network
  or this computer's personal key, except a quote the person brought in (N6, a gap below).
- **N3. Peers act only inside their own network.** A computer of network A reaches only A's rooms on
  this computer, and rooms A shares through a link. It never reaches another network's rooms,
  records, computer list or apps, and never this computer's `send`, `message` or `keep`, unless A is an
  ordinary computer's personal network (the fleet rows) or a private network other than personal that works together
  (N11). A network endpoint accepts only
  ALPN `radio-net/1` and the network's own join ALPN; the personal endpoint never accepts it, and a network endpoint never accepts
  `radio/1`, `radio-join/1` or `radio-gossip/1`. A key that is not yet a member passes only for the
  join, on a join ALPN of the network's own, never on `radio-net/1`, and only while an unused,
  unexpired join code of that network exists, under the rules of today's join row (the inviter keeps
  only the code's hash, a code has an expiry and a count of uses left); how a relay admits a newcomer
  only for that join is the relay step's to design. Test: each wrong ALPN on each endpoint is refused at the handshake; an unknown
  key on `radio-net/1`, or on the join ALPN with no open code, is refused; a `radio-net/1` peer asking for another network's record, computer list or an app's
  section is refused, and so is its `message`, `send` or `keep` on a network that doesn't work
  together.
- **N4. Down only on purpose, and reviewed when it leaves for a public network.** Content goes from a
  more trusted network to a less trusted one only when the person, or an agent they allowed, sends it.
  Anything a member not bound to that network (or, in a shared room, to a network linked with it)
  sends into an external room is held, not sent, until the person approves its exact text, optionally
  edited: a post, a status line, a deliberation's question or turn, a seat request, a room's title and
  a display name. So is anything an app marks as drafted from a higher network into a lower private
  network it is not linked with; that hold rests on the app's mark (a gap below). The agent that
  drafted a held post, which holds the private sources, never posts outside: once approved, it is
  posted by the person, or by a member bound to that network whom the person chooses, which is served
  only the approved text and that room. An edited text passes the app's leak check again before it
  leaves, and a held post records each check's result. Held posts are capped per network, and one
  approved after this computer left the network, or after its room went read only, is refused and
  never sent. Approving and declining are the person's own steps (N15). The person's own posts
  (`human`) are not held; in a network other than personal they too are the person's own step (N15).
  Test: an unbound member's post, status line, deliberation question and room title into an external
  room are each held and reach no peer until approved; an edited approval runs the leak check again;
  a declined post never leaves; an approval after leaving is refused.
- **N5. A turn takes the scope of the lowest network it read.** An agent's turn whose brief held text
  from an external room may post only into that external network. The app that runs the turn
  enforces this. Radio enforces the part it can see: `register` may bind a member to one network, and
  Radio refuses that member's posts, turns and status lines in any other network, except in rooms
  its network shares through a link. Test: a bound member's post, turn and status line in another
  network's room are each refused, and its post in a room its network shares through a link is taken.
- **N6. Up only by hand.** Nothing in a public network reaches a private one by itself: not a reply,
  a result, a seat request, a file or an outsider's question. The person brings in what they want
  (one message, several picked ones, a thread or a deliberation result) as one quote, with an
  optional note, into a room of a higher scope. Radio builds the quote from its own copy of the
  source, so an app can't forge its label: each message keeps its author, vouch state and time, the
  quote names the network it came from, and it says when messages in between were left out. Its
  author is `human`, but it is a message of its own `kind`, a quote, never a plain post, so no reader
  takes it for the person's own words; and it never starts a turn. Bringing a quote in with agents
  allowed to read it is the person's own step (N15). `read` names the member reading, and Radio serves
  a quote to a member other than `human` only when the person ticked that agents may read it (off by
  default); the reader is self-declared (a gap below). Radio, not the app, fences what it serves
  then: the quote sits between markers holding a value Radio picks at random for each answer, so the
  quoted text can't close the fence early, labelled as untrusted text from another network; reading
  it does not lower the reader's scope. Other networks' messages carry `network` and `scope` (N12),
  and the app fences them by `CONTRACT.md`. Test: a quote whose source an app altered carries Radio's
  copy; a quote with the tick off is never served to a reader other than `human`; quoted text holding
  a copy of a closing marker stays inside the fence.
- **N7. Links join two networks of one kind, by each computer's own marks.** Private with private,
  public with public, never a private network with a public one (N4 and N6 are the only way across).
  Each network's founder signs the link, and either side may unlink. A link joins exactly two
  networks and never passes through to a third: a shared room belongs to one of the two (N1), so a
  room of A that B sees through A's link is never a shared room of B's link with C. A link shares only
  the rooms either side opens as shared, where members bound to either network post without being
  held; it never shares keys, either network's other rooms, or working together. Each Radio checks
  every link against its own scope marks: a link between networks this computer marks as different
  kinds, or with a network it holds no mark for, counts as no link on this computer (its shared rooms
  are read only here, and posts into them are held as N4 holds any other), and every re-mark is
  checked again. How a shared room's posts reach a computer that is in only one of the two networks is
  the links step's to design; whichever way, each Radio checks every author against the other
  network's member list as that network's founder signed it, never on the home's word (N12).
  Unlinking leaves the shared rooms read only on each side. Test: a link request
  between a private and a public network is refused; a link signed by one founder only, or by a key
  that is not the founder's, is refused; a message from a third network through a link is refused; a
  room of A offered as a shared room of B's link with C is refused; on a computer that marks the two
  linked networks as different kinds, or marks only one, the shared rooms are read only and a post
  into them is held, and re-marking opens or closes them again.
- **N8. A shared computer never bridges.** Each of its memberships has its own key, store and
  endpoint, and it never passes a message, record, file or app operation from one membership to
  another. It holds no rooms of its own, has no `human` member and runs no agent in its personal
  memberships, so it refuses
  the room-side person-only steps (approving or declining a held post, a quote agents may read, a
  `human` post); its owner sets its marks (scope, relays, connection, working together) at its own
  command line, through N15's prompt there once N15 is built (until then, the gap on N15 below). Its personal memberships carry rooms, status
  lines and deliberations only, never `send`, `message`, `keep` or apps' sections: app operations
  reach it only through one private network other than personal that works together (N11), and the
  runner on it that takes them serves that network alone. Test: a hostile member of one of its
  networks can't reach anything of another; a `send`, `message`, `keep` or section on one of its
  personal memberships is refused; it has no room, no `human` member and no agent in its personal memberships; each
  room-side person-only step is refused; once N15 is built, a mark changes only through the prompt
  at its command line.
- **N9. Relay only, except the personal network.** Every endpoint but an ordinary computer's personal
  one (and a shared computer's first personal one) binds loopback UDP only, with the transport's
  default sockets cleared first so none stays beside it, and reaches its peers only through the
  relays its network's record names, so its peers never learn this computer's addresses. Its join
  codes, its join exchange and its computer records carry no IP address, and the address it
  publishes holds only its key and relays, never the loopback address the transport would add. It
  reaches relays over HTTPS only, with the transport's network report at its minimal settings (no
  captive-portal check, whose request goes out in plain HTTP) and the relays' QUIC address discovery
  off, so an on-path observer never sees its key beside its address. The person may allow direct connections, on their own computer, for a private membership (an internal
  network, or a shared computer's later personal one); that endpoint then takes its own fixed port
  (D31). An external membership is never direct. Test: over a test relay, a relay-only connection
  never takes a direct path, and the peer never learns a non-loopback address of this computer, from
  the connection, a join code, the join or a computer record; an `http://` relay URL is refused; no
  captive-portal request or address-discovery packet leaves.
- **N10. A stranger's relay waits for the outside review.** The person marks a relay as theirs or
  their household's, on their own computer; the mark pins the key of the relay's TLS certificate
  (relays have no other identity), checked by Radio's own certificate check on each endpoint, not
  only its URL. At join, the relays the join code names are checked before any lookup of, or
  connection to, them. While any relay a network's record names is unmarked, joining that network is refused, and a record
  change that adds an unmarked relay is not taken (this computer keeps the relays it had), until the
  outside review is recorded as passed. That review is one review of this section's boundaries by
  someone outside the project, recorded here, in its own row, when it passes. The gate is keyed on
  the relay, not the scope, since every network starts internal. Test: a join through a code naming
  an unmarked relay is refused and no packet reaches that relay; a record change adding one is not taken; a relay answering at a
  marked URL with another key is refused.
- **N11. Working together is every member's choice.** App operations (`send`, `message`, `keep`, and
  apps' sections in computer records) are carried on the endpoint of a private network other than
  personal only while every member has turned working together on, each in their own signed record
  for that network; the network record stays the founder's. Each member's flag is signed over the
  member list it agreed to, so a member admitted later reaches no app operation until every member
  has signed again with it on the list. Never on an external network, never across a link, and never
  on a shared computer's personal membership (N8). Each member decides on their own computer what the
  others may do there, private by default. Every handler call and delivery record names the
  `network` and `scope` it came from, so an app can tell a colleague's `message` from one sent by the
  person's own computers. Test, inbound: while any member's flag is off, on an external network, and
  across a link, a hostile member's `message`, `send`, `keep` or section is refused on receipt (and
  this computer's own is refused before it is sent); a member admitted after every flag was on
  reaches no app operation until every member has signed again.
- **N12. Names are bound to keys, and nothing else names the computer.** In a network other than
  personal, a participant is one membership key (one computer), shown with a fingerprint of at least
  64 bits and a display name it signs for that network; two participants whose shown fingerprints
  match are both shown in full and flagged. An admitter may sign a vouch for a name; a name nobody
  vouched for shows as unverified, and a name a second key also claims is flagged. A display name
  from another network is cleaned and capped like a member's name here, and a remote author is never
  served as `human`. Every post there is signed by its author's membership key, over the network's
  id, the room's id and the author's own count of posts, so it can't be replayed into another room or
  twice, and a receiving Radio refuses a post whose signature
  fails or whose author isn't a participant of the room, so a room's home can't forge an author; the
  home numbers the room's posts, and a receiving Radio shows a gap or a repeat in the numbers. The
  computer's own name never leaves into such a network: a room's `home` and `read`'s `author_host`
  carry the membership's fingerprint and display name there, and the network protocol's hello carries
  its own version, never Radio's. Test: an answer carries each author's fingerprint, name and vouch;
  a second key's claim to a name is flagged; a post signed by a key that is not its author's is
  refused; nothing a network is served holds this computer's name.
- **N13. Moderation is signed.** Moderators named in the network record sign removals of a
  participant, hidden messages and mutes, which every Radio applies as tombstones. A moderator may
  remove any participant but the founder; only the founder or the recovery key names or removes a
  moderator, and a removed moderator's earlier records stand, while one signed after the removal
  changes nothing. A room's home may remove a participant from that room; a hidden message is never
  served. A person's block of a participant stays on their own computer and is never sent. Test: a
  hide signed by a key that is not a moderator changes nothing; a removal of the founder changes
  nothing.
- **N14. Rates are capped per participant, under a ceiling of this computer's own.** 20 posts a
  minute and 600 a day per participant per network by default, which the founder may change in the
  record but never above a ceiling each Radio holds that no record can raise; enforced by the room's
  home and again by every receiving Radio. Status lines, seat requests, moderation and vouch records
  have caps of their own, held posts are capped (N4), and each network has a byte cap per
  participant a day and a disk cap for its rooms on this computer, past which Radio stores none of
  that network's new messages and says so. Admission follows the scale caps (a cap on the
  participants an admitter may let in). Test: the 21st post in a minute and the 601st in a day are
  refused at both; a record raising the cap above the ceiling is held to the ceiling.
- **N15. The person's own steps are confirmed outside the socket (not yet designed).** Approving or
  declining a held post, bringing in a quote agents may read, changing a scope, relay, connection or
  working-together mark, and a `human` post into a network other than personal each need a
  confirmation that Radio asks for itself, outside the socket (on its own screen or in a prompt it
  shows), so no process can give it through the socket, an agent with shell access included; a
  same-user process that reads Radio's files or drives its prompt is not stopped by it (a gap
  below). It is designed and sized with the hold. Until it is built, these steps are socket ops like
  any other (a gap below), and the steps it leaves out stay socket ops (a gap below).
  Test: each step asked for over the socket alone changes nothing until Radio's own confirmation.

### Boundaries

| Boundary | What crosses it | Control (designed) | Proven how |
| --- | --- | --- | --- |
| Another network's peer → Radio | a QUIC connection on a membership's endpoint from a key of that network, and its frames | the endpoint is that membership's alone (N2); ALPN `radio-net/1` only (N3); admission is that network's member list, as the fleet's is for the personal one; a frame naming a room, record, computer or app outside the connection's network is refused (N1, N3); posts signed by their authors (N12); rates (N14) | **not built** |
| A relay → a member | the encrypted traffic of every network the relay serves; each member's IP address; which keys talk, when and how much | the transport encrypts end to end, so a relay sees keys, addresses, times and sizes, never content; a relay admits only the member keys (or admit tokens) of the networks it serves, and a newcomer only for its join (its per-network access check, with the member sets each network sends it); a member uses only the relays its network's record names (N9), and joins a network on a stranger's relay only after the outside review (N10); one relay serving two of this computer's networks can link those memberships (a gap below) | **not built**; relays are off (the endpoint row) until this is built |
| Another network's text → apps | messages, names, status lines, deliberation turns and results, quotes | every message an app reads carries its `network`, `scope` and author (fingerprint, name, vouch); a client that has not opted in is never served another network's rooms; the contract names it untrusted text from other people, to be fenced, never taken as an instruction, never starting anything; Radio fences a quote it serves to an agent, and serves it only with the person's tick (N5, N6, N12) | **not built** |
| A local app → a lower network's room | a post, status line, deliberation turn, seat request, room title or display name from a same-user app | held for the person's review when it leaves for a public network, or when the app marks it as drafted from a higher network (N4); a bound member is refused outside its network (N5) | **not built** |
| A same-user process → the person's own steps | an approval or decline, a quote agents may read, a changed mark, a `human` post into a network other than personal | Radio's own confirmation outside the socket (N15) | **not built**, not yet designed |
| A linked network → this network | posts in shared rooms | N7, checked against this computer's own marks | **not built** |
| A shared computer → between its networks | nothing may cross; its personal memberships carry rooms only | N8 | **not built** |
| A network that works together → apps on this computer | `send`, `message`, `keep`, apps' sections | N11; the fleet rows for app messages and deliveries then hold per network, with the `network` and `scope` each came from | **not built** |

Leaving a network, or being removed from it by a moderator, closes its endpoint, drops its held
posts unsent and leaves its rooms read only; re-marking an external network internal leaves its held
posts held until the person approves or declines each;
forgetting it deletes its key, record, marks and rooms from this computer. Neither recalls what other
members already hold.

## Where secrets live

The repo needs no secrets. On a computer, Radio keeps `node.key` and, for each scoped network,
`networks/<id>.key` in the link folder. These files are 0600, and the link folder and its
`networks/` subfolder are 0700. Their secret halves never leave through the socket; `id` answers
only the personal key's public half. Recovery secrets are written once to `recovery.key` for the
personal network or `networks/<id>.recovery.key` for a scoped network, in the link folder, as 0600
files for the person to move into a password manager and delete. An interrupted scoped init leaves
files that the next scoped init removes when their network has no index row and this user owns
them. These can include
a scoped network's recovery file that the person was never shown, since that init never answered.
Relay admit tokens remain designed (§ *Several networks*). A join code's secret lives only in
the person's hands until it is used, and the inviter keeps only its hash. Radio's own releases
are signed ad hoc (D14), so Radio holds no release key; an app that signs its own updates keeps
that key itself. No token, key or password belongs in the repo; gitleaks runs in
`scripts/ci-local.sh`.

## Entry points that take untrusted input

- The socket: every op in `CONTRACT.md`, from any process of the same user (`crates/radio/src/server.rs`).
- The link (listening on the configured addresses): every connection and frame from another computer, every join code
  a person pastes, and every file a peer delivers (§ *The link*).
- The deliberation protocol (`crates/radio-panels`): every post, and any saved state a caller hands it, is
  untrusted text; it does no I/O, and its patterns are fixed, never built from a post. The daemon hands
  it each turn's body (`crates/radio/src/deliberation.rs`) and only state it wrote itself.
- `radio install`, `uninstall` and `status` arguments, from an app's installer, and the files they read
  back (`install.json`, `clients/`), each checked again on every read.
- The op commands (`crates/radio/src/cli.rs`, D16): their arguments and a body file or stdin, from the
  user's own processes, so no new trust. They build one request the socket would take from any client;
  a body is read with a bound (one byte past the 16 KiB request cap; past 8 KiB for `message`), never
  in full, and the answer is printed as it arrived once `radio-client`'s own types accept it (a line
  they refuse is `Radio did not answer`); only `ok` and `refused` choose the exit code.

## External integrations

None today, and none hosted by anyone: the first link dials only the user's own computers, at
addresses the user configured or those computers gave for themselves, and uses no service of the transport library's maker (no relay, no
address lookup). A relay, when it comes, gets its own rows here; § *Several networks* holds its design.

## Supply chain

- Lockfile committed; every cargo command runs `--locked`.
- No GitHub Actions; checks run locally (`scripts/ci-local.sh`) before a land.
- Each new dependency is pinned and reviewed when it is added.
- Release binaries are built on a maintainer's Mac by `scripts/release.sh` (D14), so they are only as
  sound as that Mac's toolchain; `SHA256SUMS` proves a download matches the upload, not the build.
- `radio-link` adds `iroh =1.3.0` with its own crates held at 1.3.0 in the lockfile (`iroh-base`,
  `iroh-dns`, `iroh-relay`, `noq`, `noq-proto`, `noq-udp`; `=1.3.0` on `iroh` alone resolves them to
  later versions; `tests/pins.rs` checks it), and `tokio =1.54.1` for its tests; the lockfile grows
  from 57 to 374 packages, none of the earlier 57 changed (name, version and checksum). The intake (crates.io,
  read 2026-10-23 when the transport was chosen): `iroh` has been published since 2022 by several
  maintainers through a publishing team, its sibling crates by the same people; of the seven pinned transport crates, the five
  with a build script only set configuration aliases (read again for this step); nothing already in the tree does
  key-addressed, authenticated QUIC. `tokio` comes with it and is used directly only by the tests. `iroh` is built with its default features off
  and only `tls-ring` and `fast-apple-datapath` on, so its `portmapper` feature (and the `portmapper`
  crate) is never compiled in.
- `radio-panels` adds `regex =1.13.1` (linear-time matching, fixed patterns) and turns on
  `serde_json`'s `preserve_order` (`indexmap`) and `float_roundtrip` for the workspace build, and,
  since the daemon calls it, for the daemon's own build: JSON objects the daemon builds keep their
  insertion order (`status.json`'s keys and the key order of the request lines the daemon binary's
  own commands send change; signed records serialize structs, never a JSON object, and the daemon
  reads requests by key) and floats parse correctly rounded. `radio-client` and `radio-rooms` still ship without
  them, and `scripts/ci-local.sh` tests them alone.
- The fuzz targets (`fuzz/`, D21) are a workspace of their own with their own lockfile, never built into a
  release, and add `libfuzzer-sys =0.4.13` with its `arbitrary 1.5.0` and `jobserver 0.1.35`;
  every package both lockfiles hold is at the same version, source and checksum, and the fuzz lockfile
  holds no other package than these three and the fuzz crate itself (`tests/pins.rs`). The intake
  (crates.io, read 2026-11-13; each checksum there equals the lockfile's): `libfuzzer-sys` and
  `arbitrary` are the rust-fuzz project's (five owners; one owner and the project's publishers team),
  first published in 2019 and 2017, with about 80 and 200 million downloads; `jobserver` is the Rust project's
  (`rust-lang/jobserver-rs`), first published in 2017, about 690 million downloads, and comes in through
  the `cc` build helper's parallel feature. `libfuzzer-sys` is `(MIT OR Apache-2.0) AND NCSA`, since it
  ships LLVM's libFuzzer; the other two are `MIT OR Apache-2.0`. Its build script compiles the libFuzzer
  C++ sources it ships (C++17, so the gate now needs a C++ compiler), and does nothing else unless
  `CUSTOM_LIBFUZZER_PATH` names a library to link instead; nothing in the tree drives a coverage-guided
  fuzzer. The property tests take no new dependency.
