# Security: radio

**Last reviewed:** 2026-11-13, when the link's wire was built. This model describes
the design every step is held to, and each step that builds a boundary updates its row.

## What this system is

A daemon, one per computer, that local apps share for rooms, the deliberation protocol and, later, the
link to other computers. It stores what its clients post and what other computers send; it reads none
of the user's own files, except a file an app hands it to send to another computer, and runs no model.
The worst outcome is a stranger getting a say in it: an
app may hand remote operations to its own handler through Radio, so a hole in Radio's
admission is a hole in that app's remote control, even though Radio never reads those messages.
The second worst is a file meant for one of the user's computers reaching anyone else, or landing
anywhere on the receiving computer but the folder its app chose.

## The link (being built: the key, the endpoint builder, the wire, the fleet record, join codes, joining, accepting, leaving, removing and blocking, and each computer's signed record, in the library; the daemon listens on its link addresses and joins, removes and leaves over them)

The first link is direct only: two computers that can already reach each other (on one network, or
over a VPN the user runs) dial each other at addresses the user configured (D15). There is no relay,
no address lookup and no port mapping yet. Each row below whose proof says **not built** is the
design the step that builds it is held to; that step replaces the proof with its tests. The steps, in
order: the endpoint and the computer's key; the wire protocol; the fleet record and join codes;
joining, accepting, leaving, removing and blocking; direct addresses; app delivery.

- **Identity is the key, and only the key.** A computer is its Ed25519 key; its endpoint id is the
  public half. The transport's TLS 1.3 handshake proves both ends hold their keys: the dialer's check
  pins the key it dialed, and the listener learns the dialer's key. A name, a fleet id, a version or
  an address a peer sends is a claim, checked against Radio's own records or ignored; it never
  identifies anyone.
- **Admission is Radio's, at the handshake, and again on every stream.** The transport lets any key
  complete a handshake with a listening endpoint. Radio's hook, which runs once the handshake
  completes and before the connection is handed to Radio, refuses every key that is not an accepted
  member on ALPN `radio/1`. A key Radio does not know passes only on the join ALPN `radio-join/1`,
  only while an unused, unexpired join code exists, and then only for the join (its own row). A
  refusal closes with one close code and an empty reason, so it tells the peer nothing. Applying a
  removal or a block closes that key's open connections in the same step, membership is checked
  again on each stream Radio accepts, and Radio never dials a removed or blocked key.
- **Nothing is replayable.** The transport's packets are bound to the connection's keys. Radio never
  sends 0-RTT (its dials keep no TLS session tickets) and never takes a connection before its
  handshake completes, so any early bytes a resuming peer sends are read only after admission; the
  transport's resumption sessions are single use. Signed records that can be forwarded over a fresh
  connection (introductions, removals, leaves, computer records) carry a version or a counter from
  their signer, and a repeated one is dropped; nothing makes counters rise, so a record held back
  and sent late is still applied once (a gap below).
- **What the transport does on its own.** The transport always runs QUIC NAT traversal, which 1.3.0
  cannot switch off: once connected, each side tells the other its bound addresses (every interface's only when bound to
  `0.0.0.0` or `[::]`, which Radio never does) and probes up to 32 addresses the other names. Radio
  limits who can reach it by binding only the local addresses the user configured, never every
  interface, and accepts the rest as a gap.
- **Raw files rest only where an app asked.** A delivered file is written only into the folder the
  receiving app registered; Radio keeps no copy of its contents on either side, and a send that can't
  reach its peer fails within the dial's 5 seconds rather than waiting in Radio.

The numbers each step tests: at most 32 link connections at once, 4 per key and 4 joins; 16
bidirectional streams open at once per connection and no unidirectional ones; Radio closes a
connection with no open stream for 30 seconds (the transport's keep-alives don't count); a frame is
read whole within 5 seconds of its stream being accepted; a file being delivered fails if no byte
arrives for 30 seconds; a dial gives up after 5 seconds;
one delivery folder holds at most 64 waiting files and 1 GiB.

## Where secrets live

The repo needs none. On a computer, the link key is the only secret Radio keeps (above), and it
never leaves through the socket: the `id` op answers the public half. A join code's secret lives only
in the person's hands until it is used, and the inviter keeps only its hash. The recovery key's
secret half is on the computer, in `recovery.key`, only until the person has moved it. Radio's own releases are signed ad
hoc (D14), so Radio holds no release key; an app that signs its own updates keeps that key itself. No
token, key or password belongs in the repo; gitleaks runs in `scripts/ci-local.sh`.

## Entry points that take untrusted input

- The socket: every op in `CONTRACT.md`, from any process of the same user (`crates/radio/src/server.rs`).
- The link (listening on the configured addresses): every connection and frame from another computer, every join code
  a person pastes, and every file a peer delivers (§ *The link*).
- The deliberation protocol (`crates/radio-panels`): every post, and any saved state a caller hands it, is
  untrusted text; it does no I/O, and its patterns are fixed, never built from a post.
- `radio install`, `uninstall` and `status` arguments, from an app's installer, and the files they read
  back (`install.json`, `clients/`), each checked again on every read.
- The op commands (`crates/radio/src/cli.rs`, D16): their arguments and a body file or stdin, from the
  user's own processes, so no new trust. They build one request the socket would take from any client;
  a body is read with a bound (one byte past the 16 KiB request cap), never in full, and the answer is
  printed as it arrived once `radio-client`'s own types accept it (a line they refuse is `Radio did not
  answer`); only `ok` and `refused` choose the exit code.

## External integrations

None today, and none hosted by anyone: the first link dials only the user's own computers, at
addresses the user configured or those computers gave for themselves, and uses no service of the transport library's maker (no relay, no
address lookup). A relay, when it comes, gets its own rows here.

## Supply chain

- Lockfile committed; every cargo command runs `--locked`.
- No GitHub Actions; checks run locally (`scripts/ci-local.sh`) before a land.
- Each new dependency is pinned and reviewed when it is added.
- Release binaries are built on a maintainer's Mac by `scripts/release.sh` (D14), so they are only as
  sound as that Mac's toolchain; `SHA256SUMS` proves a download matches the upload, not the build.
- `radio-link` adds `iroh =1.3.0` with its own crates held at 1.3.0 in the lockfile (`iroh-base`,
  `iroh-dns`, `iroh-relay`, `noq`, `noq-proto`, `noq-udp`; `=1.3.0` on `iroh` alone resolves them to
  later versions; `tests/pins.rs` checks it), and `tokio =1.54.1` for its tests; the lockfile grows
  from 57 to 374 packages, none of the earlier 57 changed (name, version and checksum). The intake (crates.io,
  read 2026-10-23 when the transport was chosen): `iroh` has been published since 2022 by several
  maintainers through a publishing team, its sibling crates by the same people; of the seven pinned transport crates, the five
  with a build script only set configuration aliases (read again for this step); nothing already in the tree does
  key-addressed, authenticated QUIC. `tokio` comes with it and is used directly only by the tests. `iroh` is built with its default features off
  and only `tls-ring` and `fast-apple-datapath` on, so its `portmapper` feature (and the `portmapper`
  crate) is never compiled in.
- `radio-panels` adds `regex =1.13.1` (linear-time matching, fixed patterns) and turns on
  `serde_json`'s `preserve_order` (`indexmap`) and `float_roundtrip` for the workspace build.
- The fuzz targets (`fuzz/`, D21) are a workspace of their own with their own lockfile, never built into a
  release, and add `libfuzzer-sys =0.4.13` with its `arbitrary 1.5.0` and `jobserver 0.1.35`;
  every package both lockfiles hold is at the same version, source and checksum, and the fuzz lockfile
  holds no other package than these three and the fuzz crate itself (`tests/pins.rs`). The intake
  (crates.io, read 2026-11-13; each checksum there equals the lockfile's): `libfuzzer-sys` and
  `arbitrary` are the rust-fuzz project's (five owners; one owner and the project's publishers team),
  first published in 2019 and 2017, with about 80 and 200 million downloads; `jobserver` is the Rust project's
  (`rust-lang/jobserver-rs`), first published in 2017, about 690 million downloads, and comes in through
  the `cc` build helper's parallel feature. `libfuzzer-sys` is `(MIT OR Apache-2.0) AND NCSA`, since it
  ships LLVM's libFuzzer; the other two are `MIT OR Apache-2.0`. Its build script compiles the libFuzzer
  C++ sources it ships (C++17, so the gate now needs a C++ compiler), and does nothing else unless
  `CUSTOM_LIBFUZZER_PATH` names a library to link instead; nothing in the tree drives a coverage-guided
  fuzzer. The property tests take no new dependency.
